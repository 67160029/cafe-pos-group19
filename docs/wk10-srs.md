# Software Requirements Specification (SRS)

## Qwerty café POS & Smart Inventory System — กลุ่ม 19

> ฉบับรวบรวมสำหรับแยกเก็บใน `docs/wk10-srs.md` จัดทำจากข้อกำหนด WK03/WK04/WK09/WK10 และโค้ด/เอกสารที่พบใน repository เนื่องจากไม่พบ SRS ต้นฉบับใน repository ณ วันที่จัดทำ เอกสารนี้ไม่ใช่หลักฐานการอนุมัติจากผู้ใช้หรือผู้สอน รายการที่ยังไม่ยืนยันระบุเป็นข้อสมมติหรือประเด็นรอตัดสินใจ

## 1. วัตถุประสงค์

ระบุข้อกำหนดสำหรับระบบขายหน้าร้านและจัดการสต็อกร้านกาแฟหลายสาขา เพื่อให้ทีมพัฒนาและตรวจรับระบบมีขอบเขตและเกณฑ์อ้างอิงเดียวกัน

## 2. ขอบเขตระบบ

ระบบเป็น Web Application ใช้ Node.js/Express, JavaScript/HTML/CSS และ MySQL รองรับพนักงานเข้าสู่ระบบเพื่อขายสินค้า ดู/จัดการออเดอร์ จัดการเมนูและสต็อก จัดคิวบาริสต้า ดูรายงาน และจัดการสาขา/พนักงานตามบทบาท

**ไม่รวมในขอบเขตที่ยืนยันได้:** payment gateway/PromptPay, ระบบสมาชิกสะสมแต้ม, สูตรวัตถุดิบและการตัดสต็อกตามส่วนผสม, การพิมพ์ใบเสร็จ, ภาษี/ส่วนลดแบบปรับแต่งได้ รายการเหล่านี้ปรากฏในความต้องการระยะแรกบางส่วน แต่ยังไม่มีหลักฐานว่าพัฒนาเสร็จ

## 3. ผู้ใช้และบทบาท

| บทบาท | การใช้งานตามระบบปัจจุบัน |
|---|---|
| Admin | จัดการพนักงานและสาขา |
| Manager | จัดการเมนู/สต็อกและดูรายงานภายในสาขาที่รับผิดชอบ |
| Cashier | สร้างออเดอร์และบันทึกวิธีชำระเงินของสาขาที่ผูกบัญชี |
| Barista | ดูคิวและเปลี่ยนสถานะการเตรียมรายการ |
| ลูกค้า | ผู้รับบริการผ่านพนักงาน; ยังไม่มีบัญชีลูกค้าหรือสมาชิก |

บทบาทและสิทธิ์อาจต่างจากการออกแบบเดิมใน WK03/WK04 ให้ตรวจสอบกับผู้สอนและโค้ดรุ่นที่จะส่ง

## 4. สภาพแวดล้อมและข้อจำกัด

- Node.js 18 ขึ้นไป, Express 5, MySQL 8 หรือ InnoDB ที่รองรับ transaction, `mysql2/promise`
- ใช้ session cookie สำหรับ endpoint ที่ต้องยืนยันตัวตน
- การเข้าถึงข้อมูลการขาย/เมนูต้องจำกัดตามสาขาและบทบาทที่ server ตรวจสอบ
- ระบบต้นแบบทำงานบนเครื่องที่กำหนดค่า `PORT` และฐานข้อมูลผ่าน `.env`; ห้ามเผยแพร่ secret
- WK02 ประเมินงบ 30,000 บาท ขณะที่ WK03 ระบุเพดาน 200,000 บาท; ต้องยืนยันตัวเลขก่อนใช้เป็น baseline

## 5. ข้อกำหนดเชิงหน้าที่

| ID | ข้อกำหนด | เกณฑ์ตรวจรับขั้นต่ำ | สถานะจากหลักฐานใน repository |
|---|---|---|---|
| FR-01 | พนักงานเข้าสู่ระบบด้วย Employee ID และ password | ข้อมูลถูกต้องสร้าง session; ผิดพลาดไม่เข้าสู่ระบบ | มี login/session ตาม WK14 |
| FR-02 | แสดงเมนูของสาขาที่เลือก พร้อมราคาและสต็อก | ไม่แสดงสินค้าหมดให้สั่ง และไม่ดึงข้อมูลข้ามสาขา | มี POS และ branch scope ตามเอกสารทดสอบ |
| FR-03 | เพิ่ม/แก้/นำสินค้าออกจากออเดอร์ และคำนวณยอดรวม | ยอดรวมเท่ากับผลรวมราคา×จำนวน; ลบรายการแล้วอัปเดตยอด | มี flow POS; ยืนยันจากหลักฐาน WK12/WK13 |
| FR-04 | ยืนยันออเดอร์พร้อมวิธีชำระเงิน | บันทึก order, order items, branch, employee, payment method; ปฏิเสธเมื่อ stock ไม่พอ | API order/payment มีรายงานผล WK13; ไม่มี gateway |
| FR-05 | ป้องกันการขายเกินสต็อกและลด stock เมื่อขายสำเร็จ | ความล้มเหลวต้องไม่สร้าง order และไม่ลด stock; การเขียนที่เกี่ยวข้องอยู่ใน transaction | มีการตรวจ transaction ตาม WK14 |

| FR-07 | จัดการเมนูและจำนวน stock | Manager เพิ่ม/แก้/ปิดเมนูและปรับจำนวน; ข้อมูลมีผลเฉพาะสาขาตามสิทธิ์ | มีหน้าและ API เมนู/สต็อก |
| FR-08 | ดูรายงานยอดขายตามสาขาและช่วงวันที่ | แสดงยอดขายและจำนวนรายการในช่วงที่ระบุ โดยไม่รวมสาขาที่ไม่มีสิทธิ์ | มีรายงาน; ตัวชี้วัดและเขตเวลาให้ยืนยัน |
| FR-09 | Admin จัดการข้อมูลสาขาและพนักงาน | Admin สร้าง/แก้/ปิดข้อมูลและกำหนดสาขา/บทบาท; ตรวจสิทธิ์ฝั่ง server | มี admin routes ตาม README; บัญชี manager/admin ตั้งผ่านฐานข้อมูลตามเอกสาร |
| FR-10 (เสนอเพิ่ม) | ค้น/สมัครสมาชิกและสะสมแต้ม | กำหนดกติกาคะแนน การคืนสินค้า และการป้องกันเลขสมาชิกซ้ำก่อนพัฒนา | ยังไม่มีโมดูล; ไม่รวม release ปัจจุบัน |

> FR-10 เป็นความต้องการระยะต่อยอดจากบันทึกสัมภาษณ์/ขอบเขตเดิม ไม่ใช่ฟังก์ชันที่ส่งมอบแล้ว

## 6. ข้อกำหนดไม่เชิงหน้าที่

| ID | ข้อกำหนด | เกณฑ์/วิธีตรวจ | สถานะ |
|---|---|---|---|
| NFR-01 | ความเร็วตอบสนอง | requirement เดิมระบุไม่เกิน 2 วินาที; ต้องกำหนดชุดข้อมูล/จำนวนผู้ใช้และทดสอบวัดผล | ยังไม่มีผล performance ยืนยัน |
| NFR-02 | ความปลอดภัยของข้อมูลประจำตัว | เก็บ password hash เท่านั้น; cookie ตั้ง HttpOnly/SameSite; จำกัดอายุ session และจำนวน login ผิด | WK14 ระบุ scrypt/session/rate limit; WK03 เคยระบุ bcrypt จึงต้องยืนยันอัลกอริทึมที่ต้องการ |
| NFR-03 | ความถูกต้องของข้อมูล | transaction สำหรับ order/stock; FK และ validation ป้องกันข้อมูลกำพร้า/ค่าผิดรูปแบบ | มีผลตรวจส่วนหนึ่งใน WK14 |
| NFR-04 | ความเป็นส่วนตัวและการแบ่งสาขา | ทุก endpoint ตรวจตัวตน บทบาท และ branch scope จาก server | มีการแก้และตรวจบางกรณีใน WK14/WK13; ต้องตรวจ regression ก่อนใช้จริง |
| NFR-05 | การใช้งาน | ทำงานบน browser desktop/tablet; ข้อความและสถานะควรเข้าใจได้ | มี wireframes และ technical UI review; ไม่มี session usability กับผู้ใช้จริง |
| NFR-06 | ความสามารถในการบำรุงรักษา | แยก route/controller/model และใช้ config ผ่าน environment | โครงสร้างโค้ดปัจจุบันแยกชั้นตาม architecture |

## 7. ข้อมูลนำเข้าและผลลัพธ์

**ข้อมูลนำเข้า:** Employee ID/password; สาขา; เมนู; จำนวนสินค้า; ตะกร้า; วิธีชำระเงิน (`cash`, `credit`, `qr` ตามระบบ); ช่วงวันที่รายงาน; ข้อมูลเมนู/stock และข้อมูลพนักงาน/สาขาสำหรับ Admin.

**ผลลัพธ์:** รายการเมนูและสถานะ stock; ยอดรวมตะกร้า; ผลสำเร็จ/ข้อผิดพลาดการสร้าง order; รายการคิวและสถานะ; ตารางสรุปยอดขาย; ข้อความยืนยัน/ปฏิเสธการจัดการข้อมูล.

Receipt ใน wireframe เป็นแนวคิดหน้าจอ/เอกสารออกแบบ ยังไม่ถือว่ายืนยันการพิมพ์ใบเสร็จจริง

## 8. กฎธุรกิจ

1. Order ต้องผูกกับสาขาและพนักงานจาก session ที่ผ่านการตรวจสอบ ไม่รับ branch scope ที่ client ใช้ข้ามสิทธิ์
2. จำนวนสินค้าที่สั่งต้องเป็นค่าบวกและไม่เกิน stock ที่ตรวจได้ใน transaction
3. เมื่อบันทึก order สำเร็จ จึงปรับ stock; หากขั้นตอนใดล้มเหลวให้ rollback ทั้งชุด
4. ราคาที่บันทึกใน order item ต้องเป็นราคาที่ server อ่านจากฐานข้อมูล ณ เวลาสร้าง order
5. รายงานและการจัดการเมนูต้องจำกัดตาม role และสาขา
6. Payment method เป็นการบันทึกประเภทการชำระเงินเท่านั้น ไม่ได้ยืนยันผลการรับชำระจากผู้ให้บริการภายนอก

## 9. สมมติฐานและประเด็นรอตัดสินใจ

- ยืนยันว่าหน่วย stock คือจำนวนสินค้าพร้อมขายต่อสาขาหรือจำนวนวัตถุดิบ
- ยืนยันขั้นตอนสถานะ order ที่อนุญาต, การยกเลิก, refund และคืน stock
- ตัดสินใจเรื่อง VAT, ส่วนลด, สมาชิก, toppings/sizes และใบเสร็จว่าจะตัดออกจาก scope หรือวาง release ถัดไป
- ยืนยันข้อกำหนด performance พร้อม workload และอุปกรณ์เป้าหมาย
- ยืนยันคำว่า “เครดิต/QR” หมายถึงเพียงบันทึกช่องทางหรือมีระบบรับชำระจริง
- ยืนยัน bcrypt หรือ scrypt ให้ตรงกับข้อกำหนดวิชาและการติดตั้งจริง
- ยืนยันงบประมาณรวมและสมมติฐานระยะคืนทุนจาก WK02

## 10. การตรวจรับระดับระบบ

1. Login สำเร็จ/ล้มเหลว และ logout ทำให้ session ใช้ซ้ำไม่ได้
2. พนักงานแต่ละ role เข้าถึงได้เฉพาะหน้าจอและ API ที่ได้รับอนุญาต
3. สร้าง order จำนวนที่ stock เพียงพอแล้วตรวจ order, order item, payment method และ stock
4. สร้าง order เกิน stock แล้ว API ปฏิเสธ โดยไม่มี order ใหม่และ stock ไม่เปลี่ยน
5. ทดสอบผู้ใช้สาขา A อ่าน/แก้ข้อมูลสาขา B ไม่ได้
6. เปลี่ยนสถานะคิวตาม workflow และตรวจว่าคิวที่เห็นสอดคล้องกับฐานข้อมูล
7. รายงานช่วงวันที่/สาขาตรงกับข้อมูล order ในฐานข้อมูล
8. จัดทำ performance test ตาม NFR-01 หลังกำหนด workload
9. ทำ usability test กับผู้ใช้จริงแยกจากการตรวจ flow โดย AI; บันทึก task, เวลา, ข้อผิดพลาด และ feedback โดยไม่สร้างผลย้อนหลัง
